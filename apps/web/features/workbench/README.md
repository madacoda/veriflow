# U1 project workbench

Open `/` to create or select a project, load the coupon fixture or review a selected saved revision, and save edits explicitly. The form currently accepts title and URL only; description/goals exist in the API contract but still need UI binding. Frozen coupon fixtures target `127.0.0.1:1111`; alternate ports currently require correcting both project and workflow URLs. See [the audit](../../../../docs/project-audit.md) for these gaps and the silent template-load error. The editor uses the v1 workflow schema, with plain-language step descriptions and labeled controls for every supported action. Generated previews and revision comparisons use the same descriptions; workflow JSON is not exposed in the UI. A revision conflict leaves the editor intact and offers the latest saved draft for comparison before the user changes the save base.

The timeline is the main workspace, with workflow setup in a narrower adjacent column on desktop and below it on smaller screens. It selects the most recent run when a project loads. The run panel sends the chosen workflow ID and exact revision to P1. It polls active runs and presents lifecycle, test outcome, ordered events, expected and actual values, evidence, and capture warnings. The default platform uses the real Chromium adapter; unavailable-adapter responses remain visible without creating a run. Screenshots render inside their matching step entries, with links to full-size images. Run-level attachments and capture warnings remain visible, including missing or partial capture. Natural-language descriptions load from the run’s exact saved revision. The collapsed sample run preview clearly labels fixture references and never fabricates screenshots. The two demo links preview target modes without changing a saved revision.

The attachment panel lists files for the selected project and uploads one file at a time through P2. A successful upload starts at **Extraction pending**. Refresh the list to see updated extraction status or a failure reason. The browser checks the file size and supported formats before upload and keeps the selected file available for retry after a failed request.

Open **Preview draft generation** to enter an objective and select templates and attachment references. **API generation** reads the template catalog and requests a project-scoped draft. The preview displays the returned provider, source references, warnings, and workflow steps. Generation is API-only; the mode selector is hidden. The editor changes when the user explicitly opens a draft. Saving remains a separate action.

API generation uses the integrated `GET /api/templates` and project-scoped `POST .../workflows/generate` routes. The catalog retains all 15 definitions and advertises `generationTemplateIds`; the generation selector uses only those supported IDs. **Testing template** keeps the nine deterministic parameter-bound templates across all six categories. The runtime uses server-only OpenAI settings. Missing configuration returns an explicit 503 without saving or running anything. The client rejects malformed drafts or source references that differ from the requested attachment set. Catalog and provider errors preserve entered inputs and editor changes. Dashboard tests cover real catalog/unavailable-provider routes and clearly mocked successful generation responses.

Terminal runs expose CSV, XLSX, and PDF download controls through P2. CSV is configured in the runtime; XLSX/PDF return 422 `unsupported_format`. The UI displays the server error and allows retry. Mocked download tests use labeled transport fixtures and do not prove valid XLSX/PDF documents. The current CSV viewport field describes the initial viewport even after responsive steps change it; this is an open audit finding.

## UI components

The web workspace uses shadcn/ui Radix Nova with Tailwind CSS v4. Theme tokens are in `apps/web/app/globals.css`. From the repository root, use `bun run --cwd apps/web shadcn add <component>` to add a registry component to `apps/web/features/ui/`. [shadcn/ui installation](https://ui.shadcn.com/docs/installation/manual) · [Tailwind CSS with Next.js](https://tailwindcss.com/docs/installation/framework-guides/nextjs)

## Dashboard verification

Run the [repository merge gate](../../../../REVIEW.md#required-merge-gate) from the checkout root. The dashboard tests capture screenshots under the Playwright test results directory for each fixture state and both coupon targets.

The real HTTP tests are opt-in so regular smoke runs can leave existing project data alone. Point `STORAGE_DIR` to an isolated temporary directory, leave `VERIFLOW_RUN_ADAPTER` unset or set it to `browser`, and set `VERIFLOW_U1_TEST_HTTP=1` before running `bun run test:smoke`. These tests cover project creation, revision conflicts without lost edits, the actual demo's observed failure and corrected pass, registered PNG retrieval, immutable earlier reports, and attachment upload/reload through P2. Target URLs use the running server's origin. Separate mocked tests verify 503 recovery, poll recovery, upload errors and project isolation. CI enables the real HTTP checks with isolated storage.

## Timeline and live verification

Generation always uses the API; there is no mode selector or local generation fallback. A generated draft is reviewed, opened in the editor, and saved explicitly before it can run.

`VERIFLOW_VERIFY_OPENAI=1 node packages/runner/scripts/verify-live-flow.mjs` is an explicitly opt-in check against a running app (`VERIFLOW_LIVE_URL` selects its origin). It calls the configured provider once, validates the generated coupon workflow before saving it, checks real pass/fail/rerun outcomes, retrieves registered screenshots, and downloads CSV reports. It retains a clearly labeled project and artifacts under `test-results/`. The normal browser suite uses an explicitly labeled model HTTP fixture and never reads real provider credentials.
